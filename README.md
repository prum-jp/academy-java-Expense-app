## 環境構築

① ブラウザで以下にアクセスする。

https://github.com/prum-jp/academy-java-Expense-app

② 右上の「Use this template」ボタンをクリックする。

③ 任意のリポジトリ名を入力して「Create repository」をクリックする。

④ 自分のリポジトリをクローンする。

```bash
git clone https://github.com/【自分のユーザー名】/【リポジトリ名】.git
cd 【リポジトリ名】
```

⑤ アプリを起動する。

```bash
docker compose up --build -d
```

初回はイメージのビルドと MySQL 初期化に数分かかることがあります。

起動後、ブラウザで http://localhost:8081 を開きます。

⑥ `main` ブランチから作業ブランチを切る。

```bash
git switch -c <ブランチ名>
```

⑦ 課題に取り組む。

実装内容を画面にリアルタイムで反映するには、コンテナを一度止めて次を実行してください。ソースは Docker 内で再コンパイルされ、保存から数秒で http://localhost:8081 に反映されます。

```bash
docker compose down
docker compose -f docker-compose.yml -f docker-compose.dev.yml up
```

⑧ 変更をコミット＆プッシュする。

```bash
git add .
git commit -m "【任意の内容】"
git push origin <ブランチ名>
```

⑨ `main` ブランチ向けの Pull Request（PR）を作成する。

不具合1件につき PR を1本作る。

## 設計書

### 1. システム概要

#### 1.1. システム名

経費精算システム『java-Expense-app』

#### 1.2. 目的

Excel や紙ベースで行われている経費精算業務を Web システム化し、申請から承認までのフローを効率化・ペーパーレス化する。

※【研修用注記】本システムは新人エンジニアのバグ調査・修正研修（実務シミュレーション）を目的としており、結合テストフェーズを想定した状態（意図的な不具合が含まれた状態）で提供される。

### 2. ユーザー権限（ロール）

本システムを利用するユーザーは、以下の2つの権限のいずれかを持つ。

- **一般社員（USER）**: 自身の経費申請、履歴の閲覧、下書き・差戻し状態の申請の編集・削除が可能。
- **承認者（APPROVER）**: 一般社員の機能に加え、部下から上がってきた申請の「承認」および「差戻し」処理が可能。

### 3. 業務フロー

1. **申請作成**: 一般社員が、勘定科目や金額を入力し、経費を申請する。
2. **承認待ち**: 申請されたデータは「承認待ち (PENDING)」ステータスとなり、承認者の画面に表示される。
3. **承認 / 差戻し処理**:
   - 承認者が「承認」した場合 → ステータスが「承認済 (APPROVED)」となり、精算処理へ回る（本システムではステータス変更のみ）。
   - 承認者が「差戻し」した場合 → ステータスが「差戻し (REJECTED)」となり、一般社員が再度編集・再申請できる状態になる。

### 4. 機能要件

#### 4.1. 画面および機能一覧

- **ログイン画面**: ID・パスワードによる認証。
- **パスワード変更画面**: ログイン中のユーザーのパスワード変更機能。
- **マイ経費一覧画面 (USER)**: 自分が申請した過去の経費一覧をステータス（未申請、承認待ち、承認済、差戻し）とともに一覧表示する機能。キーワード検索機能。
- **経費申請（入力）画面 (USER)**: 経費の基本情報と、複数行の明細（交通費、会議費など）を入力して申請する機能。
- **経費申請詳細（閲覧）画面（全権限）**: 申請内容の詳細、および「承認履歴」を閲覧する機能。
- **承認待ち一覧画面 (APPROVER)**: 自分が承認すべき「承認待ち」状態の申請一覧を表示する機能。
- **承認処理画面 (APPROVER)**: 申請内容を確認し、「承認」または「差戻し」を実行する機能。

#### 4.2. 業務ルール（データ制御要件）

- **金額制約**: 経費明細の入力金額は必ず「0円以上」でなければならない。（※マイナス金額での不正請求防止）
- **申請期限**: 経費の発生日から「3ヶ月以内」のものしか申請してはならない。
- **ステータス制約**: 経費データの編集・削除が可能なのは、ステータスが「下書き (DRAFT)」または「差戻し (REJECTED)」の場合のみである。
- **差戻しルール**: 承認者が申請を「差戻し」する場合、必ず「差戻し理由（コメント）」を入力しなければならない。
- **排他制御**: 複数人が同時に同じデータを更新した場合、後から更新したユーザーにはエラーを返し、データの上書きを防ぐこと（楽観的排他制御）。

### 5. 非機能要件

#### 5.1. セキュリティ・権限制御

- **パスワード保護**: データベースに保存するパスワードは、必ず強固なハッシュ化アルゴリズムを用いて暗号化すること。
- **アクセス制御 (IDOR対策)**: URL のパラメータなどを改ざんされても、自分に権限のない他人の経費申請詳細データの閲覧や編集はできないようにサーバー側で制御すること。
- **二重送信防止**: 登録・更新処理後はリダイレクトを行い、ブラウザの更新ボタンや連打によるデータの二重登録を防ぐこと（PRGパターン）。

#### 5.2. 履歴・監査ログ要件

- **承認履歴**: 経費の承認・差戻し処理が行われた際は、「いつ・誰が・どのようなアクションを行い・どんなコメントを残したか」を `approval_histories` テーブルに記録すること。
- **システム監査ログ**: システム内で発生したデータの登録・更新・削除などの操作は、操作ユーザー情報とともに `audit_logs` テーブルに記録すること。

#### 5.3. パフォーマンス要件

一覧画面等で複数のデータを表示する際、ループ内で都度 SQL を発行する実装（N+1問題）を避け、JOIN 等を活用して効率的にデータを取得すること。

### 7. バグの数

意図的な不具合を **9件** 仕込んでいる。

| 級 | 直しの範囲 | 内容 |
|----|------------|------|
| 初級 | 1クラス・1チェックを足せば足りる | 領収書が0件でも申請できる。サーバ側の件数チェックが無く、明細さえあれば申請ボタンも押せる |
| 初級 | 1クラス・1チェックを足せば足りる | 差戻しコメントが空でも差戻せる。サーバの必須チェックも、画面の入力チェックも無い |
| 中級 | 同じルールを画面とサーバ、または2つの SQL / 2つの画面で揃える | 承認待ち一覧を「山田」などで検索すると、件名にもログインIDにも無い申請がヒットする。漢字氏名向けの検索条件が残っている |
| 中級 | 同じルールを画面とサーバ、または2つの SQL / 2つの画面で揃える | 差戻し後に再申請すると、1次承認者ではなく最終承認者の番になる。ステップ計算が直近の申請から数えていない |
| 中級 | 同じルールを画面とサーバ、または2つの SQL / 2つの画面で揃える | 1次承認したあと、処理済みの詳細を開くと403になる。「今の番の人だけ見られる」判定と、詳細取得側の判定が揃っていない |
| 上級 | 層をまたぐ（Controller / Service / 画面 / SQL / ディスクでバラバラ） | 楽観ロックが編集の保存にしか効かない。同じデータを2タブで申請・削除・領収書操作・承認すると、後からの更新が通って上書きされる |
| 上級 | 層をまたぐ（Controller / Service / 画面 / SQL / ディスクでバラバラ） | 承認画面のボタンは今の番だけ出るが、サーバ側は「承認ルートにいる人」なら通る。番でない人が URL を直打ちすると詳細を開け、承認や差戻しもできる |
| 上級 | 層をまたぐ（Controller / Service / 画面 / SQL / ディスクでバラバラ） | 領収書の URL に閲覧チェックが無い。まだ自分の番でない申請の領収書も開け、削除後にディスクへ残ったファイルも見えてしまう |
| 上級 | 層をまたぐ（Controller / Service / 画面 / SQL / ディスクでバラバラ） | 経費や領収書を消しても、ディスク上のファイルは残る。削除処理は呼ばれているが中身が空で、別タブを再読み込みすると見える |

画面を直して通ったように見えても、サーバ・SQL・ディスク側が残っていないか確認すること。

### 8. チケットの設計

親課題は **個人学習-不具合解消** とする。子課題は次の順で進める。

| 子課題 | やること |
|--------|----------|
| 環境構築 | 本 README の手順でリポジトリ作成・起動まで行う |
| コードリーディング | 下書きの作成・編集（保存）を追い、処理の流れを把握する |
| テスト実施 / バグ起票 | テストケースを実施し、期待と違う動きを起票する |
| 不具合解消 | 起票した不具合を直す |

#### 8.1. テスト実施 / バグ起票

- 着手前に、テスト実施の工数を見積もってタスクに書く。
- 提供されたテストケースを上から順に実施する。操作は画面とアドレスバーだけとし、開発者ツールは使わない。
- 結果はスプレッドシートに記録する。期待どおりなら OK、違えば NG にする。
- NG は件ごとにチケットへ起票する。同じ不具合を二重に起票しない。
- 原因の特定や修正は、このタスクではやらない。
- 実施後、見積もりと実績を書く。

起票時の記載事項:

- 発生箇所（画面・URL）
- 再現手順
- 期待される結果
- 実際の結果
- 修正の見積もり（時間）

#### 8.2. 不具合解消

- **不具合1件につきチケット1枚、Pull Request 1本** とする。
- チケットの再現手順を先に自分でやり直して、まだ起きるか確認する。
- 原因を特定して直す。画面だけ、サーバだけ、と一箇所で終わらせず、同じルールが他の層（画面 / サーバ / SQL / ディスク）に残っていないか見る。
- 直し方の見積もりをチケットに書き、着手する。
- 直したら、元の再現手順をもう一度画面操作だけで確認する。通ったら、似た操作（戻る、別タブ、別ユーザー、URL 直打ちなど、チケットの状況に応じて）でも再発しないか見る。
- 見積もりと実績をチケットに残す。
- `main` 向けの PR を作成し、メンターの Approve をもらう。

完了条件:

- 再現手順どおりに操作して、期待どおりになること。
- 同じ不具合が別ルートで残っていないこと。
- GitHub の PR をメンターに提出し、Approve をもらうこと。
- 見積もりと実績が書かれ、自身で起票したチケットが完了になっていること。
